# コミット & プルリクエスト作成

作業ツリーの変更を、安全なガードレールを守りながらコミットし、プルリクエスト（PR）を作成します。`git` と `gh`（GitHub CLI）を使う、Claude Code と Codex の両方で動く手順書です。

## ワークフロー

### 1. 前提を確認する

- `git rev-parse --is-inside-work-tree` で git リポジトリ内か確認する。違えばその旨を伝えて終了する。
- `git status` と `git diff`（ステージ済みは `git diff --staged`）で変更内容を把握する。**変更が何もなければ**、コミットするものがない旨を伝えて終了する。空コミットを作らない。

### 2. ブランチを確認する

`git branch --show-current` で現在のブランチを確認する。デフォルトブランチ（`main` / `master` など。`git remote show origin` か `git symbolic-ref refs/remotes/origin/HEAD` で確認）に**直接コミットしない**。

- デフォルトブランチ上にいる場合は、変更内容から推測した名前で feature ブランチを切ってから作業する（例: `feat/...`、`fix/...`、`chore/...`）。ブランチ名に迷う場合や変更が大きい場合はユーザーに一声かける。
- すでに作業ブランチ上にいればそのまま使う。

### 3. 差分をレビューしてコミットメッセージを作る

`git log --oneline -10` で**そのリポジトリの慣習**（言語・プレフィックス・粒度）を確認し、それに合わせる。多くのリポジトリは Conventional Commits（`type(scope): 要約`）を使う。

- **type**: `feat` / `fix` / `docs` / `style` / `refactor` / `test` / `chore` など、変更の実態に合うものを選ぶ。
- **言語**: 直近のコミットが日本語なら日本語、英語なら英語で書く。リポジトリに合わせる。
- 要約は命令形・現在形で簡潔に。必要なら本文で「なぜ」を補う。
- 無関係な複数の変更が混在している場合は、論理単位ごとに分けてコミットすることを検討・提案する。

**コミット例:**
入力: JWT を使ったユーザー認証を追加した
出力: `feat(auth): JWT ベースのユーザー認証を実装`

### 4. ステージしてコミットする

意図した変更だけをステージする（`git add <path>`）。`git add -A` は、無関係なファイルやゴミを巻き込まないことを確認できるときだけ使う。

コミットメッセージの末尾には、実行しているエージェントに応じた共著者トレーラーを付ける（リポジトリの慣習に合わせる。不要なら省く）。

- Claude Code: `Co-Authored-By: Claude <noreply@anthropic.com>`
- Codex: そのエージェントの慣習に従う。

### 5. push する

`git push -u origin <branch>` でリモートに push する。upstream 未設定なら `-u` で設定する。push は外向きの操作なので、ユーザーから明示的に依頼されているか、文脈上明らかに許可されている場合に行う。曖昧なら確認する。

### 6. プルリクエストを作成する

`gh pr create` で PR を作る。ベースはデフォルトブランチ。

- **タイトル**: コミット要約に準じる。複数コミットなら全体を表す要約にする。
- **本文**: 変更概要・背景（なぜ）・確認内容を、リポジトリの慣習・言語に合わせて書く。テンプレート（`.github/PULL_REQUEST_TEMPLATE.md`）があれば従う。
- 作成後、PR の URL をユーザーに伝える。

```sh
gh pr create --base <default-branch> --title "<title>" --body "<body>"
```

## 原則

- **破壊的・確定的な操作はしない**: `push --force`、`reset --hard`、ブランチ削除、履歴改変などはユーザーの明示的な依頼があるまで行わない。
- **デフォルトブランチに直接コミット／push しない**: 必ず作業ブランチを経由する。
- **秘密情報・個人情報を含めない**: 認証情報・トークン・メールアドレス等をコミットメッセージや PR 本文に書かない。diff にシークレットが含まれていれば push 前に警告する。
- **勝手にバージョンを上げない**: `version` の bump はリポジトリの方針とユーザーの依頼に従う。
- **捏造しない**: 変更がない、リポジトリでない、`gh` 未認証などの場合は、その事実を伝えて止まる。実行していない手順を「やった」と書かない。
- 既存の履歴やリモートの状態を大きく変える前にはユーザーに一声かける。
